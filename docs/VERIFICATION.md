# What was checked

The verification uses **real MongoDB**, not an in-memory substitute. Test data is fictional and generated by the tests. The results describe local checks, not the employer's hidden grader or a hosted production system.

## Recorded run

**100 tests passed, with no failures or skips, in 13.40 seconds.** The saved [test summary](evidence/test-summary.json), [scale result](evidence/scale-evidence.json) and [server result](evidence/server-evidence.json) contain the measured results and timestamps. The environment was Python **3.12.14** and MongoDB **7.0.15**. Exact durations are a snapshot from that run and will vary by machine.

The full command is:

```bash
python -m pytest --require-mongo --run-scale --junitxml=test-results/junit.xml
```

Set `MONGO_TEST_URI` first, pointing to a local test server. Keep port 8000 free for the Uvicorn test. The tests use a fresh random database for each fixture and remove only databases they created.

## A hand-calculated analytics example

The analytics fixture deliberately includes employees with no records, a future joiner, a mid-month joiner, weekend work, half days and an orphan attendance record.

| Expected result | Why |
|---|---|
| Ops headcount = 4 | Includes eligible employees with no logs; excludes the future joiner |
| Ops present days = 3.5 | Counts weekday presence, with half days worth 0.5 |
| Ops average hours = 5.8 | The five completed presence records total 29 hours; 29 / 5 = 5.8 |
| Mid-month joiner working days = 13 | Counts weekdays beginning on the employee's joining date |
| Ranks = 1, 2, 2, 2 | Three employees share the second-highest late total, so limit 2 includes all four people |
| A later lower score has rank 5 | Competition ranking leaves gaps after ties |
| Rounded 3.505 = 3.51 | Half-up differs from ties-to-even |
| Rounded daily rate 1/32 = 0.0313 | Rate rounding uses four decimal places, half-up |

Expected values are asserted explicitly; the tests do not simply call the implementation's calculation helpers to generate the report answers.

## The 100,000-record check

The scale test generates **1,000 employees and 100 attendance dates** across five departments, then starts the app against those existing records. It checks results as well as speed:

- The February attendance list has 28,000 matching records and returns the requested page.
- The employee monthly report has 20 working/present days and 100% attendance.
- Each department has 200 employees, 4,000 present days and an average of 8 hours.
- A rank limit of 1 returns all 250 employees tied at rank 1.
- The trend returns exactly 92 daily rows, with weekday rates and weekend nulls.

Every required explain path showed **IXSCAN** and no **COLLSCAN** in this dataset; lookup execution counters also showed no collection scans. The raw query timing and startup measurements are in [scale-evidence.json](evidence/scale-evidence.json). Timings include local request handling, not just MongoDB execution time.

The trend query is the most expensive path: it performs daily lookups and joins. The recorded 92-day run took a few seconds, while the other measured paths were faster. An index scan alone does not prove a query is cheap. For much larger data, precomputed daily summaries with correct adjustment after corrections would be the first performance improvement to evaluate.

## Deliberate limits and assumptions

There is no authentication or authorization: `regularized_by` is supplied text. A protected demo must use fictional data, and a real deployment needs verified identities and access control. `/admin/explain` is useful for the assignment but should require an administrator in a real service.

The API uses the employee's current department and shift. There is no effective-dated department/shift history. Working days are Monday through Friday without public holidays. Records are unique per employee and attendance date, so split shifts and multiple punches in one day are outside this contract.

Seeded data is assumed to follow the supplied model, including valid dates, valid statuses and unique natural keys. The documented legacy missing fields are handled. Invalid pre-existing duplicates can prevent unique-index creation; health then reports 503 rather than pretending the service is ready.

The app does not silently retry a conflicting manual correction. A caller must read the current record and decide whether its intended change still makes sense. Direct database access can bypass application rules; this prototype does not make MongoDB itself a tamper-proof audit system.
